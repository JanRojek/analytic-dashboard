# Frontend / backend gaps

The backend was inspected before implementation: .NET Minimal APIs, application handlers, EF Core/PostgreSQL, Identity cookies, and DuckDB CSV-to-Parquet processing. Existing integration tests cover real authentication and the import → profile → query → dashboard/widget path. No backend code was changed.

## Already connected

The API adapter uses the actual `/auth`, `/projects`, project dataset, dashboard, and widget endpoints through the frontend `/api` proxy. It supports account registration/confirmation/login/reset/logout; project create/list/read/rename/delete; CSV import; dataset read/profile/delete; grouped analytics; and dashboard/widget create/list/read/delete operations. Backend errors remain errors; there is no automatic demo fallback.

## Missing capabilities and current boundaries

| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Preparation recipes** make cleanup understandable and repeatable.              | `mocks/preparation.ts` supports trim, fill, drop-empty, and duplicate removal across all local rows, then creates a separate dataset. Connected mode explains its unavailability. No transformation API exists.                                                                                                                                          | Persist ordered recipes, execute preparation jobs, produce versioned outputs, and retain source lineage and validation results.                                                                          |
| **Canvas layout and chart editing** let users develop a coherent dashboard.      | Order, half/full widths, chart titles, types, and query overrides live in `mocks/editor.ts`. New chart records use the API in connected mode; subsequent edits remain local. There are no dashboard/widget update or layout endpoints.                                                                                                                   | Atomic dashboard document/layout save plus widget update APIs, with concurrency/version checks.                                                                                                          |
| **Recoverable drafts and saved presentation** support reopening unfinished work. | Browser drafts and saved editor documents are separate; presentation uses the saved layout/configuration with current widget records and dataset versions. Creating/removing widgets takes effect immediately, independently of the local Save action. Exploration keeps one local draft per mode/user/project. These do not synchronize across devices. | Saved analyses and draft/revision APIs, account-owned persistence, conflict handling, and optional published snapshots.                                                                                  |
| **Import status and recovery** help users understand asynchronous work.          | Import returns dataset/version/job IDs, but no endpoint exposes job state or errors. The frontend polls dataset readiness every 2.5 seconds for about a minute, then offers another check. Pending and failed cannot be distinguished.                                                                                                                   | Read import-job status/error/progress; retry/cancel where supported; expose latest version state.                                                                                                        |
| **Dataset naming and project context** improve recognition.                      | Project descriptions exist only in the demo. The import name is implemented by naming the uploaded CSV because the backend derives dataset names from filenames. Existing dataset rename and broader metadata are unavailable.                                                                                                                           | Dataset rename/import display-name fields; project descriptions; separate original filename and display name; optional updated timestamps.                                                               |
| **Complete row browsing** supports deeper investigation.                         | Profiles return the first ten rows. Search/sort is explicitly limited to that preview. The shared import preview currently limits both modes to 10 MB and 20,000 rows; these are frontend prototype limits.                                                                                                                                              | Paginated/filterable row APIs and scalable preview/upload validation, with documented server upload limits.                                                                                              |
| **Richer quality insight** improves confidence beyond completeness.              | Real profiles expose type, null count, numeric min/max/average. The UI describes missing values, not an overall accuracy score. Distributions, distinct counts, outlier checks, and quality rules are absent.                                                                                                                                            | Expanded profiling statistics and persisted data-quality checks with clear definitions and provenance.                                                                                                   |
| **Richer questions** support more demanding analysis.                            | One grouping column and one measure with Sum/Average/Min/Max/Count are real. CSV is the implemented source type. Database/SaaS connectors, scheduled refresh, permissions for project collaborators, and dataset version selection remain future work; the prototype does not display working controls for them.

## Persistence and verification limits

Demo workspace data uses the versioned `aperture.demo.v1` browser store. Editor documents are scoped by mode, user, project, and dashboard. Local storage holds no passwords or authentication tokens; authentication uses server-issued HttpOnly cookies. Clearing site storage removes local work. Stored demo data is not uploaded when a user later signs in.

The live backend was not running on ports 5151/7208 during the integration review, and local SMTP port 1025 was unavailable. API contracts and automated frontend tests were checked; a complete live authentication/import session has not been runtime verified. See [frontend setup](frontend/README.md) for the required origin and service configuration.
