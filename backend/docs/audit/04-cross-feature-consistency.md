# Audyt A — spójność między funkcjami backendu

Data: 2026-11-06. Drugi przebieg diagnostyczny. Nie zmieniono kodu, testów ani konfiguracji; nie uruchamiano testów, migracji ani instalacji. Ścieżki i numery linii odnoszą się do aktualnych plików w `backend`.

## Zakres i sposób oceny

Przed analizą przeczytano [01-architecture.md](01-architecture.md), [02-findings.md](02-findings.md) i [03-refactoring-roadmap.md](03-refactoring-roadmap.md). Ponownie porównano implementacje wszystkich 30 handlerów Application, pięciu rodzin endpointów, siedmiu repozytoriów EF, IUnitOfWork/AppDbContext oraz używane kontrakty i wyniki. Weryfikowano rzeczywisty przepływ argumentów, rezultatów, zapisu i wyjątków. Identity i procesor importu uwzględniono jako odmienne granice operacji, a nie jako zwykły CRUD.

Nie analizowano klienta ani działającego wdrożenia. Ocena skutków po stronie UI jest zatem scenariuszem opartym na kontrakcie HTTP, nie potwierdzeniem konkretnego zachowania frontendu. Nie przeprowadzono świeżej kompilacji lub pomiarów. Wynik poprzedniego wykonania istniejącej DLL testów jednostkowych opisuje raport 01; w tym przebiegu go nie powtarzano.

**Spójność oznacza przewidywalną semantykę, nie identyczny kod.** Różne odpowiedzi dla metadanych, pracy asynchronicznej, autoryzacji i zapisu są często uzasadnione. Nowe ID poniżej odnoszą się wyłącznie do dodatkowych obserwacji. AUD-001–024 pozostają odrębnymi ustaleniami; ponowne wskazanie przykładu z tamtej listy nie zwiększa liczby wykrytych błędów.

### AUD-025 — stan „dataset istnieje, ale nie ma gotowej wersji” nie ma wspólnego kontraktu

- **Typ / priorytet / pewność:** Consistency, Medium, Confirmed dla bieżącego mapowania; wpływ na istniejący frontend wymaga weryfikacji. Nie jest to potwierdzona utrata danych ani luka autoryzacji.
- **Porównane lokalizacje:** `src/AnalyticDashboard.Application/Datasets/GetDatasetById/GetDatasetByIdHandler.cs:36-68`; `src/AnalyticDashboard.Application/Datasets/GetDatasetRows/GetDatasetRowsHandler.cs:41-56`; `src/AnalyticDashboard.Application/Datasets/GetDatasetProfile/GetDatasetProfileHandler.cs:39-56`; `src/AnalyticDashboard.Application/Analytics/QueryDataset/DatasetQueryExecutor.cs:58-77`.
- **Mapowanie HTTP:** `src/AnalyticDashboard.Api/Endpoints/DatasetEndpoints.cs:190-209,372-373,427-435,510-519`; dla widgetów `src/AnalyticDashboard.Api/Endpoints/WidgetEndpoints.cs:95-106`.
- **Aktualne zachowanie:** Pending dataset bez CurrentVersionId ma metadane 200 z `version: null`; rows i profile zwracają NotFound/404; query oraz widget-data zwracają InvalidQuery/400 z tekstem „Dataset has no ready version.”. Również nieistniejący/niedostępny zasób może dać 404, a nieprawidłowa nazwa kolumny — 400.
- **Mechanizm / konsekwencja:** brak Ready to stan zasobu, a nie to samo co błędne parametry query lub nieistnienie datasetu. Klient nie dostaje stabilnego, wspólnego rozróżnienia i może wymagać osobnych reguł per endpoint albo interpretacji angielskiego komunikatu. Różne statusy same w sobie nie naruszają protokołu HTTP; problemem jest niejawna semantyka.
- **Scenariusz:** po Accepted importu, zanim worker skończy pracę, użytkownik otwiera metadata, profile, rows i widget-data tego samego datasetu. Te funkcje opisują tę samą niegotowość jako trzy rodzaje sytuacji. Trzeba zweryfikować, czy klient celowo unika takich wywołań i czy kontrakt jest mu znany.
- **Kierunek:** zachować 200 metadanych, które są dostępne także podczas importu. Dla operacji wymagających danych określić wspólny rezultat `NotReady` lub stabilny kod w ProblemDetails oraz jawne mapowanie HTTP. Nie narzuca się 202 dla GET ani jednego statusu wszystkim funkcjom; jeden opis semantyki wystarczy, jeśli statusy są celowo różne. Dostępny `import-status` powinien być dokumentowany jako sposób sprawdzenia postępu.
- **Korzyść:** klient rozróżnia oczekiwanie na import, brak zasobu i niepoprawną query bez parsowania wiadomości; łatwiejsze testy stanów przejściowych.
- **Testy przed zmianą:** ta sama macierz nonexistent / foreign / Pending / Failed / Ready dla metadata, rows, profile i query, a także widgetu przypiętego do Pending. Nie rozszerzać komunikatów o status cudzych datasetów. W testach nie wolno uznać fizycznego braku pliku Ready za zwykłe Pending.
- **Wysiłek:** Medium. **Ryzyko regresji:** Medium — statusy/kształt odpowiedzi używane przez klienta. **Zależności:** weryfikacja użyć klienta i state machine importu, bez powtarzania AUD-007.

### AUD-027 — API odrzuca szczegóły niepoprawnej konfiguracji widgetu

- **Typ / priorytet / pewność:** Consistency, Medium, Confirmed. To utrata informacji kontraktu, nie błąd atomowości zapisu.
- **Porównane lokalizacje:** `src/AnalyticDashboard.Application/Widgets/UpdateDashboardWidgets/UpdateDashboardWidgetsHandler.cs:104-129`; `src/AnalyticDashboard.Application/Widgets/UpdateDashboardWidgets/UpdateDashboardWidgetsResult.cs:11-12,22`; `src/AnalyticDashboard.Api/Endpoints/WidgetEndpoints.cs:291-295` wobec `src/AnalyticDashboard.Api/Endpoints/ProjectEndpoints.cs:65-70,236-241` i `src/AnalyticDashboard.Api/Endpoints/DatasetEndpoints.cs:430-435,513-518`.
- **Aktualne zachowanie:** handler zna WidgetId i powód niepoprawnej konfiguracji każdego widgetu, ale endpoint zwraca jedynie „One or more widget configurations are invalid.”. Projekty i rows zwracają `ValidationProblem` z nazwanym polem, a query datasetu przekazuje przyczynę pod kluczem Query. Podstawowe błędy widgetów wykryte wcześniej w endpointcie mają jeszcze inny, pojedynczy opis w `WidgetEndpoints.cs:171-195`.
- **Mechanizm / konsekwencja:** np. niepusta nazwa mająca 201 run przechodzi wczesny check endpointu; reguła domeny generuje konkretną przyczynę, która znika przy mapowaniu. Przy całym zestawie widgetów użytkownik nie wie, który element wymaga poprawy. Dokładnie ten sam rodzaj błędu formularza jest w innych funkcjach możliwy do przypisania do pola.
- **Scenariusz / dowód:** dwa widgety z poprawną geometrią i dostępnym datasetem; jeden ma zbyt długi Title, GroupByColumn lub MeasureColumn. Request jest prawidłowo odrzucony i nic nie zostaje zapisane, ale odpowiedź nie wskazuje elementu. Istniejący test `tests/AnalyticDashboard.IntegrationTests/Widgets/UpdateDashboardWidgetsEndpointTests.cs:313-352` bada status i brak zmian, nie zachowanie przyczyny w HTTP.
- **Kierunek:** przekazać ograniczoną, bezpieczną diagnostykę walidacji z identyfikatorem widgetu lub ścieżką pola w uzgodnionym formacie. Najprościej wykorzystać znany w projekcie ValidationProblem albo małe `errors` extension; nie budować generycznego frameworka błędów. Zachować ograniczenie liczby elementów/błędów. Nie przekazywać raw wyjątków infrastruktury.
- **Korzyść:** możliwa poprawa konkretnego elementu formularza; klient nie zgaduje przyczyny na podstawie długości lokalnie; nie jest potrzebne ponawianie zapisu po jednej zmianie na ślepo.
- **Testy:** response zawiera właściwe WidgetId/ścieżkę i przyczynę, nie zdradza cudzych datasetów, a cały zestaw nadal pozostaje niezmieniony. Sprawdzić granice długości i kilka błędnych elementów przy dopuszczalnym rozmiarze listy.
- **Wysiłek:** Small. **Ryzyko regresji:** Medium — klient może już używać generic detail; rozszerzenie powinno zachować przewidywalny status. **Relacja do starych ustaleń:** lista kolizji i jej koszt to AUD-003; niniejszy punkt dotyczy odrębnej utraty już policzonych błędów konfiguracji.

### AUD-026 — różne znaczenie pustej listy pod nieistniejącym rodzicem

- **Typ / priorytet / pewność:** Consistency, Low, Confirmed dla zachowania. Ujednolicenie jest sugestią kontraktu, nie obowiązkową poprawką bezpieczeństwa.
- **Porównane lokalizacje:** `src/AnalyticDashboard.Application/Datasets/GetDatasets/GetDatasetsHandler.cs:27-43`; `src/AnalyticDashboard.Api/Endpoints/DatasetEndpoints.cs:128-151` wobec `src/AnalyticDashboard.Application/Dashboards/GetDashboards/GetDashboardsHandler.cs:14-30`, `src/AnalyticDashboard.Api/Endpoints/DashboardEndpoints.cs:91-104`, `src/AnalyticDashboard.Application/Widgets/GetWidgets/GetWidgetsHandler.cs:18-41` i `src/AnalyticDashboard.Api/Endpoints/WidgetEndpoints.cs:45-59`.
- **Aktualne zachowanie:** brak własnego projektu daje 404 przy GET jego datasetów, ale 200 `[]` przy GET dashboardów. Nieistniejący lub niedostępny dashboard daje 200 `[]` przy GET widgetów. Predykaty repozytoriów nadal filtrują owner/project; żadna z tych odpowiedzi nie ujawnia zawartości cudzych zasobów.
- **Mechanizm / konsekwencja:** tylko GetDatasets osobno sprawdza rodzica. W pozostałych funkcjach filtr bez pasujących rekordów wygląda tak samo jak istniejący rodzic z pustą kolekcją. Klient wspólnie obsługujący zakładki projektu nie może w ten sam sposób odróżnić pustej listy od usunięcia rodzica.
- **Scenariusz:** projekt jest usunięty, po czym klient odświeża listę datasetów i dashboardów ze starym projectId. Dostaje 404 w jednej zakładce i pusty sukces w drugiej. Bez frontendu nie przesądza się, że to obecnie błąd UX.
- **Kierunek:** wybrać i udokumentować politykę kolekcji zagnieżdżonych: 404 niedostępnego rodzica albo celowe puste filtrowanie. Jeśli 404, korzystać z kontroli scope rodzica i dopiero potem listować; jeśli 200, jawnie opisać to jako semantykę wyszukiwania. Nie dodawać pre-checku każdej kolekcji tylko dla identycznej liczby linijek. W obu wariantach obcy i nieistniejący rodzic muszą pozostać nierozróżnialni.
- **Korzyść:** mniej wyjątków w wspólnej obsłudze pustych i usuniętych widoków; testy dokumentują świadomą decyzję.
- **Testy:** istniejący pusty rodzic / nieistniejący / obcy, w tych samych trzech rodzinach list. GetDatasets ma już test obcego projektu (`tests/AnalyticDashboard.IntegrationTests/Datasets/GetDatasetsEndpointTests.cs:152-177`).
- **Wysiłek:** Small. **Ryzyko regresji:** Medium — zmiana 200 na 404 jest zmianą obserwowalnego kontraktu. Brak potrzeby pilnego wdrożenia przed AUD-001–019.

### AUD-028 — repozytorium joba ukrywa szerszą granicę commit

- **Typ / priorytet / pewność:** Consistency / sugestia projektowa, Low, Confirmed dla zakresu zapisu. Nie stwierdzono nieatomowego commitu w aktualnym procesorze.
- **Porównane lokalizacje:** `src/AnalyticDashboard.Application/Datasets/Persistence/IImportJobRepository.cs:25-27`; `src/AnalyticDashboard.Infrastructure/Repositories/ImportJobRepository.cs:90-95`; `src/AnalyticDashboard.Infrastructure/Services/Import/ImportJobProcessor.cs:88-104` wobec `src/AnalyticDashboard.Application/Common/Persistence/IUnitOfWork.cs:3-5`, `src/AnalyticDashboard.Application/Widgets/UpdateDashboardWidgets/UpdateDashboardWidgetsHandler.cs:195-199` i `src/AnalyticDashboard.Infrastructure/DependencyInjection.cs:37-43`.
- **Aktualne zachowanie:** SaveChanges na IImportJobRepository zapisuje cały współdzielony AppDbContext. Procesor zmienia jednocześnie DatasetVersion, Dataset i ImportJob, a następnie wywołuje zapis przez port nazwany repozytorium jobów. Repozytorium pobiera cały work item jako śledzone encje (`ImportJobRepository.cs:18-52`).
- **Mechanizm / konsekwencja:** czytelnik lub autor kolejnego writera może uznać zapis za ograniczony do joba. Faktyczna atomowość zależy od wspólnego scope i zachowania trackingu trzech typów; wymiana repozytorium na implementację zapisującą tylko joba złamałaby istniejący, niejawny kontrakt. Jest to sprzężenie utrzymaniowe, nie dowód obecnej awarii.
- **Scenariusz:** przyszły refaktor rozdziela repozytoria lub wprowadza dla jobów inny scope; nazwa i interfejs nie sygnalizują, że aktualna finalizacja publikuje także wersję datasetu. Test wyłącznie statusu joba mógłby tego nie wykryć.
- **Kierunek:** przy refaktorze importu uczynić zakres zapisu jawnym: użyć istniejącego IUnitOfWork w obsłudze śledzonego work item albo zachować małą operację persistence jednoznacznie opisującą finalizację importu. Do wyboru według docelowej odpowiedzialności; nie trzeba wdrażać obu wariantów. Już dziś można udokumentować kontrakt zamiast przebudowywać repozytoria.
- **Korzyść:** autor zmian widzi, że Ready + CurrentVersionId + Completed są jednym zapisem. Zmniejsza się ryzyko rozszczepienia poprawnej atomowości podczas napraw AUD-004/007/008.
- **Testy przed zmianą:** odczyt w nowym scope potwierdza trzy spójne zmiany po sukcesie i brak częściowej finalizacji po błędzie. Zachować obecny test procesora; rozszerzyć o kontrolowaną awarię według wcześniejszej roadmapy.
- **Wysiłek:** Small dla jawnego kontraktu; nie obejmuje przebudowy lease/recovery. **Ryzyko regresji:** Medium przy zmianie implementacji persistence. **Uzasadnione wyjątki:** ProjectRepository.Add i PendingDatasetImportRepository.Create mogą nadal zapisywać własną, spójną operację; ExecuteDelete/ExecuteUpdate i UserManager nie muszą być przepisywane na stage + UoW.

## Walidacja, wyjątki i HTTP — proponowana minimalna konwencja

### Odpowiedzialności walidacji

1. Endpoint obsługuje składnię i transport: obecność elementu payloadu, parsowanie enum, multipart, przekształcenie layout request w WidgetLayout. Handler ma otrzymać reprezentację, na której może bezpiecznie wykonać przypadek użycia.
2. Handler sprawdza uprawnienia przez scoped persistence, stan procesu i spójność zestawu, np. Revision, wszystkie ID, kolizje i dostępność datasetów. Nie polega wyłącznie na atrybucie RequireAuthorization.
3. Encja/value object zachowuje reguły własnego poprawnego stanu. Handler mapuje znane naruszenie wynikające z danych użytkownika na wynik, jak CreateProject. Nie należy usuwać ochron encji tylko dlatego, że endpoint podobne dane już sprawdza.
4. Baza rozstrzyga unikalność i referencje również podczas wyścigu. Tłumaczyć konkretny SQLSTATE i constraint w miejscu granicy persistence; nie zamieniać dowolnego DbUpdateException w konflikt użytkownika.

Punkty 1–3 są już widoczne w `src/AnalyticDashboard.Api/Endpoints/WidgetEndpoints.cs:153-245`, `src/AnalyticDashboard.Application/Widgets/UpdateDashboardWidgets/UpdateDashboardWidgetsHandler.cs:35-129` i `src/AnalyticDashboard.Domain/Entities/Widget.cs:90-124`. Analogią prostszego przypadku jest `src/AnalyticDashboard.Application/Projects/CreateProject/CreateProjectHandler.cs:22-40`. Konkretne luki długości/enum/nazwy mają AUD-012/013/014/024 — nie zgłoszono ich ponownie jako nowych „problemów spójności”.

Krótkie, powtarzane kontrole null/blank mogą być celowe na dwóch granicach; nie należy ich usuwać automatycznie. `InvalidEntityNameException` dziedziczy po ArgumentException (`src/AnalyticDashboard.Domain/Entities/InvalidEntityNameException.cs:3-6`), dlatego warunek `ArgumentException or InvalidEntityNameException` w handlerze widgetów (`:119`) ma redundantny drugi człon. To drobna korekta czytelności przy zmianie pliku, bez odrębnego AUD i bez mierzalnego wpływu na wydajność.

### Wyniki oczekiwane i wyjątki

Własność/brak zasobu, InvalidName/InvalidQuery i konflikt Revision to przewidywalne wyniki operacji. Awaria połączenia, fizyczny brak pliku Ready, błąd programistyczny lub niemożliwe przejście stanu pozostają wyjątkami wymagającymi obserwowalności. Nie unifikować wszystkich do bool albo „Success=false”. `ImportJob.MarkCompleted` pilnuje przejścia Running → Completed (`src/AnalyticDashboard.Domain/Entities/ImportJob.cs:70-80`); jego wyjątek nie jest odpowiednikiem błędu pola nazwy w HTTP.

Różne wyjątki w obsłudze zapisu są technicznie uzasadnione: `src/AnalyticDashboard.Infrastructure/Repositories/ProjectRepository.cs:32-40` obsługuje DbUpdateException z inner PostgresException dla SaveChanges, a `:82-88` sam PostgresException dla ExecuteUpdate. Nie „naprawiać spójności” przez kopiowanie identycznego catch do obu ścieżek. IUnitOfWork tłumaczy concurrency w `src/AnalyticDashboard.Infrastructure/Data/AppDbContext.cs:45-54`; repozytoria wywołujące zwykły AppDbContext.SaveChanges nie przechodzą przez tę jawną implementację interfejsu. W obecnych użyciach token dashboardu jest zapisywany przez właściwą ścieżkę. Regułę dla przyszłych writerów trzeba zachować świadomie.

Default w switchu `UnreachableException` (np. `Projects/CreateProject/CreateProjectHandler.cs:56`) i `InvalidOperationException` (np. `Analytics/QueryDataset/QueryDatasetHandler.cs:49-50`) oznaczają niedopasowany wewnętrzny wariant, nie oczekiwany błąd użytkownika. Różnica typu jest stylistyczna; warto wybrać jedną konwencję przy nowych wynikach, bez osobnej abstrakcji lub globalnego catch.

### Kształt błędów HTTP

Minimalny kierunek: znane błędy pól mają przewidywalne `errors`, konflikty i stany procesu stabilny kod/typ oraz bezpieczny opis, a brak dostępu nie ujawnia istnienia zasobu. Nie wymaga to jednego generycznego envelope dla wszystkich sukcesów i błędów.

Obecnie Project zwraca puste Unauthorized/NotFound (`src/AnalyticDashboard.Api/Endpoints/ProjectEndpoints.cs:94-96,120-121`), a Dashboard jawny ProblemDetails (`src/AnalyticDashboard.Api/Endpoints/DashboardEndpoints.cs:113-138`). To potwierdzona różnica reprezentacji, ale bez dowodu awarii klienta nie uzasadnia nowego Medium finding. Dodatkowo normalne odrzucenie przez middleware może mieć inną pustą odpowiedź niż ręczna walidacja ClaimsPrincipal; deklaracja ProducesProblem nie generuje odpowiedzi sama. Przy uzgadnianiu kontraktu uwzględnić zarówno middleware, jak i branch endpointu, zamiast testować tylko nagłówek test auth.

Auth musi zachować wyjątki semantyczne: Forgot/Resend celowo nie zwracają UserNotFound (`src/AnalyticDashboard.Application/Auth/ForgotPassword/ForgotPasswordHandler.cs:23-35` i `Auth/ResendConfirmation/ResendConfirmationHandler.cs:23-42`), confirm/reset łączą niektóre przypadki błędnego linku (`src/AnalyticDashboard.Api/Endpoints/AuthEndpoints.cs:135-147,445-450`). Mechaniczne „wszędzie 404 na brak encji” pogorszyłoby bezpieczeństwo.

## Dobre wzorce do przeniesienia i kolejność prac

1. **Project jako wzór prostego zapisu:** reguła domeny → jawny wynik walidacji → konkretny constraint → HTTP. Przenosić zachowanie tam, gdzie brakuje obsługi znanego błędu; nie kopiować całej struktury typów do każdego GET.
2. **Widget jako wzór zapisu zestawu:** wszystkie walidacje przed stage/mutacją, jeden commit oraz token concurrency w SQL. Przenosić tę granicę do porządkowania importu, zachowując różnice lifecycle.
3. **DatasetQueryExecutor jako wzór faktycznego współdzielenia:** analytics i widget-data używają tego samego sprawdzania scope, wersji i zapytania (`QueryDatasetHandler.cs:17-25`, `GetWidgetDataHandler.cs:38-46`). To konkretna korzyść; analogiczne współdzielenie nie jest automatycznie potrzebne dla podobnych DTO.
4. **Zbiorczy odczyt wersji:** `src/AnalyticDashboard.Application/Datasets/GetDatasets/GetDatasetsHandler.cs:45-57` unika pętli zapytań. Nie zastępować go helperem „get current version” wywoływanym osobno dla każdej encji.

Priorytetem nadal są wcześniejsze High i potwierdzona utrata plików. W ramach najbliższej zmiany walidacji można zabezpieczyć i wdrożyć AUD-027. AUD-025 wymaga najpierw krótkiego uzgodnienia semantyki stanów i testów macierzy, AUD-026 — decyzji klienta o polityce pustych kolekcji, AUD-028 — jawności granicy persistence przy już planowanym refaktorze importu. Nie tworzyć etapu masowego wyrównania nazw, typów Result, using lub liczby warstw.

Kryterium weryfikacji tych zmian: zachowane ownership scope, przewidywalny publiczny kontrakt, brak częściowych zapisów oraz testy realnego zachowania. Ten raport proponuje cztery uzupełnienia diagnozy; żadnego nie zaimplementowano.
